# تقييم OpenHuman — هل يفيد سارة؟ وكيف ومتى؟

**التاريخ**: 2026-08-29 · **أعدّه**: Lead Implementation Architect · **الحالة**: تقرير بحثي (ليس ADR)
**المصدر**: https://github.com/tinyhumansai/openhuman

---

## 1. الخلاصة التنفيذية (الحكم في 4 أسطر)

**OpenHuman مشروع ممتاز كمرجع معماري، وخاطئ كاعتماد كود لسارة.** قيمته الحقيقية لنا:
مجموعة أنماط مجرّبة تثبت صحة قراراتنا الجاهزة، وتقدّم 3-4 أفكار نستعيرها *كتصميم* (لا ككود)
في مواعيد محددة مرتبطة بمهام Sprint 2/3 وv1.1. أما الدمج الفعلي فيُحسم من ثلاثة عوائق قاطعة:
الترخيص (GPL-3.0 عدوى مقابل MIT لدينا)، الحزمة (Rust/Tauri desktop مقابل Python 3.12 async headless)،
والتكلفة (أدواته الأقوى تعمل داخل اشتراك — ينتهك $0.00 المطلق).

**القرار**: نراقب المشروع ونستعير الأنماط في مواعيدها، ولا ندمج شيئاً في v1.0 إطلاقاً.

وكلاء على رسوم بيانية durable)، **الباحث العميق** (مسح ويب وبيانات قبل انتهاء سؤالك).

## 3. ثلاثة حواجز صلبة أمام الدمج (لماذا "لا" لنسخ الكود)

1. **الترخيص — GPL-3.0 مقابل MIT-نا**: سارة مرخّصة MIT (2026, Madaar Team). أي نسخ/دمج
   لكود GPL-3.0 في سارة **يجبر** إعادة ترخيص سارة بأكملها GPL-3.0. استعارة الأنماط
   والأفكار المعمارية لا تدخل في حقوق النشر؛ أما نسخ كودهم أو ترجمته برمجياً فتدخل.
2. **النموذج الاقتصادي — الاشتراك**: أدواته الأقوى (بحث Exa مُدار، توليد صور/فيديو، اجتماعات)
   "مشمولة بالاشتراك" = كلفة شهرية. حتى كأداة مستقلة، أي استخدام لقدراته المدفوعة ينتهك
   ADR-08 ($0 مطلق). يبقى خياراً فقط بوضع BYOK/محلي موجه إلى OmniRoute (§6).
3. **حزمة وشكل غير متوافقين**: Rust + Tauri + Node 24 + CMake + تطبيق سطح مكتب، بينما سارة
   حزمة Python 3.12 خادمية عديمة واجهة على VPS مجاني. لا توجد نقطة لصق طبيعية.

## 4. مصفوفة الميزات: ما يهمنا / ما لا يهمنا (ولماذا)

### 4.1 أنماط نتعلّم منها الآن (استعارة تصميم — لا كود)

| النمط عند OpenHuman | مكانه في سارة | لماذا يفيدنا |
|---|---|---|
| **TokenJuice** — ضغط مخرجات الأدوات قبل النموذج (حتى 80% وفّر توكنز) | مهام 2.2/2.3 (أجساد بريد غير موثوقة قبل التصنيف)، وscout في v1.1 | مجمعاتنا المجانية محدودة الحصة؛ ضغط جسد البريد قبل المصنّف = طلبات أقل، أقل بلوغ سقف quota، زمن استجابة أقصر. **أهم نمط في التقرير كله** |
| **Split-brain** — وكيل رد فعل سريع + نواة استدلال عميق | يطابق حرفياً تقسيمنا `FAST_MODEL`/`PRIMARY_MODEL` (مهمة 1.2 المنجزة) | تحقق خارجي صامت من قرارنا؛ لا فعل مطلوب |
| **Auto-fetch** — حلقة مزامنة كل 20 دقيقة تغذي الذاكرة | مهام 2.2 (Gmail watch) و2.4 (Daily Brief) | يؤكد أن "polling دوري → ضغط → ذاكرة" معمارية صحيحة بدل الاعتماد على Pub/Sub المدفوع |
| **Memory Tree** — ضغط البيانات إلى أشجار Markdown *مُدرّجة النقاط* معكوسة كـ vault Obsidian | بنيتنا (PARA + Zettelkasten، `User_Info.md`، `Dialect_Notes.md`) | نفس الفكرة بالضبط (مستوحاة هم من Karpathy). الإضافة الجديرة بالسرقة لاحقاً: **درجة جودة لكل عقدة ذاكرة** لتقليم/ترتيب الملاحظات آلياً بدل تضخم الـ vault |

### 4.2 مرشحات فعلية بمواعيد محددة (v1.1 وما بعدها)

| القدرة | متى | التقييم |
|---|---|---|
| **STT محلي (in-process Whisper)** | Sprint 3.2 — تحويل ملاحظة صوتية واردة إلى نص | فجوة حقيقية عندنا (لا حل STT مثبت بعد). الخيارات: whisper.cpp على PC عبر bridge، أو Groq Whisper (طبقة مجانية سخية). يُحسم قرار 3.2 — وهو مستقل عن OpenHuman لكنه يثبت أننا لسنا وحدين في المسار |
| **نمط الباحث العميق** (sweep → compress → synthesize) | v1.1 — tech-hardware-scout | نستعير *منهجية* المسح ثم الضغط ثم التركيب، منفذة بأدواتنا عبر OmniRoute — لا وظيفتهم المدفوعة |
| **Workflows durable + approval-gated** (tinyflows) | v1.2+ اختياري | فلسفتهم (اقتراح الوكيل → مراجعة بشرية → بوابة موافقة → تشغيل durable) هي نفسها ADR-03 عندنا بمستوى أنضج. لا canvas مرئي لنا — YAGNI لملكٍ واحد |

### 4.3 ما لا يجب أن ننظر إليه إطلاقاً (مع السبب — كما طلبت)

| الميزة | سبب الاستبعاد |
|---|---|
| **التخزين المحلي / SQLite Memory Tree كتخزين** (وbackend agentmemory) | **عندنا أوبسيديان git-backed بالفعل** (PARA + Zettelkasten) — قيمة العقل عندنا في الـ vault المُدار بإصدارات، لا في قاعدة محلية موازية. نتدارس *منهجية التدرّج* فقط (§4.1) لا مخزنهم |
| **17 قناة مراسلة** (Discord/Slack/WhatsApp/iMessage…) | سارة owner-only عبر تيليجرام (ADR-02 + ADR-06) — قنوات متعددة = سطح هجوم أوسع وتعقيد بلا مستفيد |
| **الواجهة الرسومية، الثيمات، Theme Studio، التميمة/Mascot** | سارة صوتية-نصية على تيليجرام، headless على VPS — لا سطح مكتب لنا |
| **توليد الصور/الفيديو، البحث المدار (Exa)، الاجتماعات (Meet/Zoom)** | تعمل ضمن **اشتراكهم** = كل استخدام ينتهك $0 (ADR-08). واجتماعات Zoom خارج نطاقنا كلياً (نطاقنا مكالمات تيليجرام v1.1) |
| **اقتصاد الوكلاء** (tiny.place، x402 USDC، صفقات) | عملات رقمية وبازارات وكلاء — يناقض ملكية-واحد و$0، ويضيف سطحاً أمنياً خطيراً |
| **Privacy Mode كخاصية** | نحتاجه أصلاً بنيوياً: owner-only + كتم غير-المالك في middleware + أرضية القائمة البيضاء — أشد صرامة من مفتاحهم |
| **تفاوض النماذج subscription routing** | لدينا OmniRoute + تثبيت GLM الملزم — أقوى تحكماً وأرخص (صفر) |

| المرحلة | الفعل |

## 6. المخاطر التي يجب ألا نغفلها

1. **Beta مبكرة فعلاً**: 326 issue مفتوحاً، عمر 6 أشهر — أنماطهم تتغير؛ لا نبني على تفاصيل تنفيذهم بل على الأفكار المستقرة.
2. **جاذبية الاشتراك**: كل شيء عندهم مصمم ليدفعك نحو اشتراكهم — أي "تجربة" بأدواتهم الأصلية تسحبك خارج $0. الأنماط مجانية؛ الأدوات المدمجة لا.
3. **انزلاق النطاق**: سارة قلب تنفيذي مركّز لملك واحد؛ OpenHuman منصة شاملة. تحويل سارة إلى نسخة مصغرة منه يخسر هويتها (وقد فُضّل اتساق النطاق الضيق في ADR-07).
4. **عدوى GPL**: حتى "الإلهام من الكود" — إن قرأنا تنفيذاً بالتفصيل ثم كتبنا كوداً مشابهاً حرفياً، فهذا مشتق. نستعير *الفكرة والسلوك* من الوثائق، ونكتب من مواصفاتنا.

## 7. الخلاصة

> **OpenHuman = مصداقية خارجية لقراراتنا + قائمة أنماط مستحقة بمواعيدها.**
> نأخذ منه الآن: لا شيء كوداً، وأنماط TokenJuice (عند 2.3) وauto-fetch (عند 2.4/2.2).
> لاحقاً: STT قرار مستقل عند 3.2، ونمط الباحث عند v1.1، وأداة مصاحبة مشروطة عند v2.0.
> نتجاهل: التخزين المحلي، القنوات المتعددة، الواجهة، الوسائط المدفوعة، واقتصاد الوكلاء.
